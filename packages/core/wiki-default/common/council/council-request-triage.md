사용자 요청이나 버그 보고를 문자 그대로 받아 바로 배정하면, 해석이 틀리거나 원인이 코드가 아니어서 위원 작업이 통째로 버려진다.
배정 전에 캡처·질문 한 줄·git 확인으로 해석과 재현 조건부터 맞춘다.

## 언제 쓰나
- 화면 이동·재배치·목록화 요청("○○ 자리에 넣어줘")
- "판정은 그대로, 이펙트만 N배 오래" 같은 연출 요청
- "고친 거 아냐?", "또 나온다" 같은 회귀 보고
- "반드시 X를 골라야 넘어간다", "버튼이 안 켜진다"처럼 코드 조건과 안 맞는 보고

## 방법
### 화면 배치 요청: 옮기기인가 새로 만들기인가
- "목록은 ○○ 탭 자리에 구성해줘"는 기존 캔버스 화면을 그 칸에 옮기라는 뜻일 수 있다(HTML 목록을 새로 만들라는 뜻이 아니라).
- 배정 전에 기존 화면 캡처를 council_show로 보여 주고 "이 모습 그대로 그 칸에?"를 묻거나, 지시에 "기존 그리기를 재사용해 같은 모습으로"를 명시한다.
- 착수 직후 잘못을 알았으면 [실행 중인 위원 지시 바꾸기](common/council/council-change-running-instruction)대로 정지 후 재배정.

### "이펙트만 N배 오래": 구현 방식을 먼저 묻기
- 두 방식이 있다: (1) 이펙트 전체를 1/N 속도로 재생 (2) 판정 시점은 맞추고 끝부분만 늘림. (1)은 착탄·폭발 그림이 실제 피해보다 늦게 보인다.
- 배정 전에 두 방식을 사용자에게 한 줄로 묻거나 지시에 방식을 명시한다.
- 판정 불변 확인: 렌더 전용 타임라인 사본을 두고, 바꾸기 전 커밋의 전투 결과(GOLDEN)와 같은지 테스트한다.

### "고친 버그가 또 나온다"
- 원인은 대개 셋: 수정이 그 빌드에 없음 / 적용 조건(플랫폼·레벨 분기) / 반쪽 수정.
- `git log --all -S <심볼>`·`git log --all --grep`으로 커밋을 찾고 `git branch -a --contains <커밋>`으로 빌드 포함 여부를 확인한다.
- 수정 diff에서 조건 분기(`DESKTOP ? XL : 기본`, `level === 30` 등)를 찾는다.
- 사용자에게 어디서 봤는지(웹/데스크톱/버전)와 캡처를 받은 뒤 배정한다.

### "버튼이 안 켜진다"가 코드 조건과 안 맞을 때
- 버튼 조건식(ready/disabled)과 화면의 필수·선택 칸 라벨을 대조한다.
- 입력이 채워진 전체 화면 캡처를 받아 어느 칸에 무엇을 넣었는지 본다(예: 이미지를 필수 칸이 아닌 선택 칸에 넣은 경우).
- 원인이 입력 위치면 "그 칸에 넣으면 됨 / UI가 다른 칸도 받게"를 사용자에게 묻는다.

## 주의할 점
- 사용자 용어를 문자 그대로 받지 않는다. 원인 미상 버그로 위원 여럿에게 맡기기 전에 캡처부터.
