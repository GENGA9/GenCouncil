외부 라이브러리를 우리 도구와 비교하라고만 맡기면, 위원은 가장 손쉬운 입력(우리 테스트용 합성 열화 이미지, 가까운 프로젝트 산출물)을 쓴다. 합성 열화는 우리 도구를 튜닝한 모델이라 우리에게 유리하고, 가까운 산출물은 상대 도구가 노리는 입력이 아닐 수 있다. 그러면 "도입 불필요" 같은 결론이 편향된다. 아래 조건을 처음 지시에 넣는다.

## 언제 쓰나
- 외부 이미지 처리 라이브러리(예: AI 픽셀아트 격자 복원)를 우리 도구와 비교·도입 검토할 때
- 비교 결과가 "우리 것이 낫다"로 나왔는데 코퍼스·실행 조건이 한쪽에 유리했는지 의심될 때

## 방법
### 지시에 넣을 조건
- 코퍼스: 상대 라이브러리가 공개한 벤치 코퍼스(라이선스 확인), 또는 제3자 코퍼스를 반드시 하나 포함한다. 우리 합성셋은 보조로만 쓴다.
- 대상 입력 확인: 실제 입력 후보가 그 도구의 대상 입력인지 먼저 확인한다(예: 정답 격자가 있는지 눈으로 보거나 메타데이터로). 대상이 아니면 정확도 비교가 아니라 거짓 양성 검사로 따로 분류한다.
- 속도: 상대가 권장하는 실행 조건(워커·스레드 켬)으로도 잰다. 끄고 쟀으면 그 사실을 표에 적는다.
- 전처리(배경 제거 등): 상대 README 권장 흐름과 생략한 흐름 두 가지로 돌린다. 한쪽만 돌리면 결과가 그 흐름 탓인지 구분이 안 된다.
- 막히는 조합은 끄지 말고 원인을 적는다(끄면 상대 조건이 불리해진다).

### 브리핑 템플릿
- 무엇을 비교 / 코퍼스 3종(상대 공개·우리 합성·실제 대상 입력) / 지표 / 실행 조건 / 측정 못 한 것은 못 했다고 적기.
- 잘 먹힌 완료 조건: 한 명령으로 재현되는 벤치(예: `run.mjs`), 자동 생성 표와 사람이 쓴 해석 분리, 비교 png, 기존 테스트 통과, "숫자 지어내기 금지 / 못 한 것은 적기", "src 수정 금지·외부 저장소 읽기 전용".

## 주의할 점
- 큰 결과 파일(예: 12MB results.json)은 커밋하지 말고 요약만 남기게 한다.
- 위원 성향: sonnet은 재현성·한계 기록은 좋지만 코퍼스를 손쉬운 쪽으로 고른다([claude sonnet](models/claude-sonnet)).
