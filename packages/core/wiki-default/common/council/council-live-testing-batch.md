사용자가 앱을 직접 테스트하거나 영상·화면을 보며 수정을 연달아 적는 동안에는 위원이 캡처용 서버·브라우저를 띄우면 테스트를 방해한다. 첫 수정부터 앱 실행을 막고, 수정은 모았다가 한 번에 반영한다.
사용자가 "모아 줘"라고 하면 모음을 의장 기억에만 두지 말고 작업 목록에 쌓는다. 실제로 최종 통합 지시에 "새 음성 생성 금지"를 넣어 사용자가 요청한 '톤 보정'이 음량 보정만 된 채 끝나 "이건 왜 안 했어?"라는 지적을 받았다.
생성 자원(로컬 GPU, ComfyUI 대기열)이 하나뿐이면 지적마다 설계 위원을 병렬로 두고, 생성은 묶음 위원 하나가 한 번에 한다.

## 언제 쓰나
- 사용자가 실시간으로 테스트하며 수정 요청을 계속 보낼 때
- 편집 프로그램·화면을 보며 피드백을 연달아 주고 "바로 배정하지 말고 모아 줘"라고 할 때(영상·게임·UI 검토 단계 모두)
- 드래프트 검토 중 사용자가 수정사항을 하나씩 말할 때(아래 '기록만 → 계획 세워 → 수정 실행')
- 영상 구간별 수정 지적이 수십 개 연달아 오고, 생성은 동시에 하나만 돌 수 있으며, 수정마다 같은 생성기 소스와 생성 결과 파일(스토리보드 json·md·뷰어, 작업표)을 건드려 병렬 위원끼리 머지 충돌이 계속 날 때

## 방법
### 실시간 테스트 중 배정
- 첫 수정부터 지시에 기본 문구를 넣는다: "앱을 띄우지 말 것, 코드+타입검사+테스트까지". 캡처 완료 조건은 뺀다.
- 금지 문구 없이 먼저 보낸 위원은 stop한 뒤 handover(reason에 바뀐 지시)로 교체한다.
- 같은 파일을 고치는 작업은 todo로 등록해 두고 앞 작업이 머지된 뒤 배정한다.
- 머지할 때마다 확인 못 한 항목을 체크포인트에 쌓아 마지막 보고에 목록으로 넘긴다.
- 화면 확인은 테스트가 끝난 뒤로 미루고, 사용자가 볼 몫이면 그렇게 적는다.

### "모아 줘": [모음] 작업으로 쌓기
- 새 지적은 그때마다 council_add_task로 제목 앞에 '[모음]'을 붙여 todo로 만든다. 설명에 캡처 경로·타임코드·사용자 선택(예: 후보 ①)을 적는다. 배정은 하지 않는다.
- 사용자가 결정해야 하는 항목은 그 자리에서 council_ask_user로 묻고, 답을 작업 설명에 적는다.

### 기록만 → "계획 세워" → "수정 실행" (사용자 규칙)
- 사용자가 수정사항을 하나씩 말할 때마다 바로 위원을 배정하면, 아직 말하지 않은 수정과 겹치거나 순서가 꼬인다.
1. 사용자가 수정사항을 말하면 **기록만** 한다: council_checkpoint의 '수정사항 기록' 목록에 더하고 "기록했습니다(N건)"로 짧게 답한다. 배정·생성하지 않는다.
2. 의장이 찾은 알려진 문제도 같은 목록에 '의장 기록'으로 구분해 둔다.
3. 사용자가 "계획 세워"라고 하면 기록된 수정사항 전체로 계획(묶음·순서·위원·도구·예상 시간)을 세워 보여 준다.
4. 사용자가 "수정 실행"이라고 하면 그때 위원을 배정해 실행한다(통합할 때는 아래 '반영해' 점검을 그대로 한다).

### "반영해": 통합 지시에 빠짐없이
- 모음 todo를 전부 열어 통합 지시에 번호를 붙여 옮긴다.
- 지시의 '하지 말 것'(예: 새 생성 금지)이 어떤 모음 항목과 충돌하지 않는지 대조한다. 충돌하면 그 항목은 지시에 예외로 명시해 허용하거나 별도 작업으로 뺀다.
- 통합 결과를 받으면 모음 todo를 하나씩 done/doing으로 닫으며 빠진 것이 없는지 확인한다.
- 일괄 반영 지시가 오면 남은 위원을 기다렸다가 버전·전체 테스트·배포·패키징을 위원 한 명에게 묶어 맡긴다. merge_base 뒤 마지막에 원격 백업한다.

### 생성 자원이 하나일 때: 설계 위원 병렬 + 생성 묶음 위원
- 지적이 들어오면 바로 지적 하나당 '설계 위원'을 배정해 병렬로 돌린다. 사용자에게는 "생성은 묶음에서 한 번에"라고 알린다.
- 설계 위원이 맡는 일: 원인 진단, 키프레임 그리기, 생성기 소스 수정, 계획서 작성까지.
  - 생성 결과 파일은 그림을 그리려고 다시 만들어도 되지만, 커밋 전에 git checkout으로 되돌린다. 커밋에는 생성기 소스, 그림, 계획서만 넣는다.
  - 생성기 소스에서 자기 구간 항목만 건드린다.
  - 생성 파이프라인 스크립트(작업표 생성기 등)는 수정하지 말고, 고칠 내용을 계획서에 적는다.
- 계획서가 모이면 '생성 묶음 위원'(상위 모델, [claude opus](models/claude-opus)) 하나에게 넘긴다. 이 위원이 할 일:
  - 충돌로 의장이 머지하지 못한 위원 브랜치를 자기 worktree에서 직접 git merge한다.
  - 생성기를 다시 돌린다.
  - 모든 계획서를 반영한다.
  - 해당 구간만 다시 생성하고 새 판으로 조립한다.
- 묶음 위원 지시서에는 병합할 브랜치 목록과 충돌 파일, 반영할 계획서 경로, 다시 생성할 구간, "GPU 대기열에서 다른 사람 작업을 취소하지 말 것"을 적는다.
- 충돌난 브랜치는 '검토 중'으로 두고, 묶음 위원이 병합하면 완료로 바꾼다. 종료할 때 '미병합' 경고가 나오면 `git merge-base --is-ancestor`로 이미 main에 들어갔는지 확인한다([위원 결과 합치기·종료](common/council-merge/council-merge-finish)).
- 설계 위원 배정 뒤 사용자가 덧붙인 지적은 패킷에 없으면 처리되지 않는다 → 별도 작업으로 등록하고, 그 위원이 끝나면 반영 여부를 확인해 보완 작업을 붙인다([claude sonnet](models/claude-sonnet)).
- 그림 결과는 다른 모델([gemini-4-argon](models/gemini-4-argon))이 독립 검수한다.
- 생성물 충돌 자체를 없애는 법은 [합본 생성물 충돌 없애기](common/git/split-combined-generated-files).

## 주의할 점
- 먼저 낸 지시에 금지 문구가 없으면 그 위원이 앱을 띄운다. 첫 지시부터 넣는다.
- opus 위원은 지시의 금지 조항을 글자 그대로 지켜 요청 일부를 빠뜨린 적이 있다([claude opus](models/claude-opus)).
