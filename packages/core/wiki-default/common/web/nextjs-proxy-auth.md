Next Route Handler가 서버 전용 백엔드 토큰을 붙이고 백엔드가 토큰만 검사하면, 비로그인 사용자도 데이터를 받는다. 기존 프록시를 복사해 새 프록시를 만들면 구멍이 늘어난다.
백엔드는 사용자 세션도 검사하고, 프런트가 쿠키를 넘기도록 먼저 배포한 뒤 백엔드를 바꾼다. Vercel 서버리스를 거치는 요청은 본문 4.5MB 제한이 있다.

## 언제 쓰나
- Next(Vercel 등) 프런트 + FastAPI 등 백엔드 구조에서 프록시 라우트를 만들거나 점검할 때
- 새 프록시 경로를 라이브에 반영하고 확인할 때
- 프록시를 거친 요청만 백엔드에서 401이 날 때
- 프록시를 거치는 파일 업로드가 413일 때

## 방법
- 백엔드 라우터에 토큰 검사 + 사용자 세션 의존성(`current_user` 류)을 둔다.
- 프록시는 요청 Cookie를 백엔드로 전달하고, 응답은 `Cache-Control: no-store`/private.
- 배포 순서: 프런트 배포 확인(새 페이지 200 또는 배포된 JS 청크에서 바뀐 문구 검색) → 백엔드 재시작 → 프록시 경로가 404가 아님(예: 비로그인 401) 확인. 백엔드에 로그인 검사를 먼저 넣고 재시작하면 쿠키를 안 넘기는 옛 프런트 때문에 로그인 사용자도 401.
- 새 프록시 완료 조건에 비로그인 curl 상태 코드 확인을 넣고, 기존 프록시 전체도 한 번 점검한다.

### 프런트 배포 반영 확인: 메인 HTML이 아니라 JS 청크에서 문구 grep
- Next.js는 UI 문자열을 `/_next/static/chunks/*.js`에 넣는다. 메인 HTML에 새 문구가 없다고 미배포로 판단하지 않는다.
- `curl -s https://<도메인>/ | grep -o '/_next/static/chunks/[^"]*\.js' | sort -u` → 각 경로를 `https://<도메인><경로>`로 curl → `grep -q "<문구>"`.
- 10분 안에 50초 간격으로 폴링한다. Vercel은 push 후 약 2분에 반영됐다.
- 문구는 HTML에서 `&lt;` 같은 엔티티로 나올 수 있으니 두 형태를 함께 grep한다.

### 헤더 합치기: `Headers` 객체를 스프레드하지 않는다
- `{ ...backendHeaders(), Cookie: cookie }`처럼 합치면 백엔드가 401. `Headers` 인스턴스는 열거 가능한 자기 속성이 없어 스프레드하면 `{}`가 된다(Authorization이 사라진다). TypeScript도 못 잡는다.
- 합칠 값을 헤더 만드는 함수의 인자로 넘기거나, `new Headers(base)`를 만든 뒤 `set`한다.
- 프록시를 추가하면 실제 프록시를 거치는 요청을 브라우저나 curl로 한 번 확인한다.

### Vercel 경유 업로드: 본문 4.5MB 제한
- Vercel 서버리스 Route Handler를 거치는 요청은 본문이 4.5MB를 넘으면 413이 난다.
- 클라이언트에서 총합 예산(3.5MB)을 정해 해상도·품질 단계를 내려 맞추고, 넘치면 뒤쪽 파일을 뺀다.
- 413 응답은 JSON이 아닐 수 있으니 상태 코드로 먼저 분기한다.

## 주의할 점
- 백엔드 상태를 그대로 넘기는 프록시(`new Response(body,{status})`)에서 새 경로가 404면 대개 "프런트 배포 안 됨"이 아니라 옛 백엔드에 라우트가 없는 것이다. 프록시 경로 404로 프런트 배포를 판단하지 않고, "404면 백엔드 재시작 보류" 같은 조건을 넣지 않는다(서로 기다린다).
- 비로그인 401은 프런트 배포 증거가 아니다.
- 백엔드가 파일을 304로 줄 때 프록시 쪽 처리는 [FastAPI·Starlette 함정](common/python/fastapi-starlette-pitfalls). 업로드 폼 E2E 테스트는 [Playwright 캡처·테스트 함정](common/web/playwright-pitfalls).
