위원은 지시에 적힌 금지만 지키고 빈틈은 스스로 채운다. 캡처는 열어 보지 않고 통과로 보고할 수 있고, 의장이 쓰는 wiki_read·memory·advisor 도구가 자율 위원에게는 없을 수 있어 위키 경로만 주면 절차를 못 읽는다.
전용 포트·git merge 허용은 이제 위원 기본 규칙에 들어 있다. 아래 문구를 해당하는 지시에 넣고, 의장은 결과를 직접 확인한다.

## 언제 쓰나
- 위원에게 위키·공유 기억에 적힌 절차를 따르게 할 때
- 확인용 개발 서버·브라우저 캡처가 필요한 위원 지시를 쓸 때
- 위원에게 git merge(베이스·통합 브랜치)를 시킬 때
- 검증 위원이 캡처로 '통과'를 보고했을 때

## 방법
### 위키 경로와 핵심 절차를 함께
- 의장이 먼저 관련 위키를 읽고, 배정문에 다음을 모두 넣는다:
  1. 위키 경로
  2. 이번 작업에 필요한 정확한 적용 순서·명령 또는 제약
  3. 도구가 없을 때 쓸 같은 절차(이미 읽어 옮긴 내용)
  4. 성공 증거와 한계
- 위원은 도구가 있으면 원문을 읽고, 없으면 옮겨 준 절차를 적용하며 "위키 원문은 못 읽었다"를 보고한다.
- 도구가 없는 것은 모델의 수행 실패와 구별해 기록한다. 위원이 없는 도구로 상담했다고 주장하지 않게 한다.
- 위키가 요구하는 필수 승인·권한을 이 대체 절차로 우회하지 않는다.
- 예: 이미지 수정 지시에 "이전 이미지를 SAME 참조로 쓰고 변경 영역 밖 인물·구도·빛은 고정"을 직접 넣자 위키를 못 읽는 위원도 작업을 이어 갔다.

### 개발 서버: 전용 포트
- 이제 프로그램이 자동으로 한다: 위원 기본 규칙에 "확인용 서버는 전용 포트, 공용 포트는 쓰지도 끄지도 않기, 끝나면 닫기"가 들어 있다. 지시에는 포트 번호만 적는다(예: 전용 5191 `--strictPort`, 공용 5183).
- 사고(공용 포트에 위원 worktree vite가 남아 사용자가 보는 공용 서버가 위원 worktree를 서빙)가 나면 의장은 프로세스를 못 끄므로 worktree 정리 전에 사용자에게 꺼 달라고 한다.

### git merge를 시킬 때
- 이제 프로그램이 자동으로 한다: 지시에 git merge가 명시되면 그 merge는 허용된다(위원 기본 규칙). 지시에 `git merge <브랜치>`를 명시하고, diff를 git apply로 옮기지 말라고만 한다(조상이 이어지지 않아 뒤에 add/add 충돌이 난다).
- 이미 diff로 옮겼으면 다음 위원이 merge로 조상을 잇는다.

### 캡처 검증: 파일을 열어 본다
- 검증 위원이 '통과'라 해도 캡처가 팝업뿐이거나 파일명·보고와 내용이 다를 수 있다(코드만 읽고 PNG를 안 여는 경우가 있다).
- 지시에 팝업 닫기 절차와 "캡처 파일을 열어 내용을 확인"을 완료 조건으로 넣는다.
- 의장은 대표 PNG를 Read로 직접 연다. 틀리면 다음 위원 지시에 "팝업을 닫고 재촬영"과 파일명을 지정한다.
