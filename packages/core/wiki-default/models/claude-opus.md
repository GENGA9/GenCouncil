원인 모를 버그, 큰 merge·통합, 긴 생성 파이프라인(분석→그림→생성→조립), 구조 리팩터링·밸런스, 다른 위원이 실패한 작업의 원인 재진단처럼 길고 판단이 많은 일을 한 번에 끝내는 데 가장 믿을 만하다.
약점은 작업이 길고, 지시를 글자 그대로 지키다 목적을 놓치거나 반대로 범위를 스스로 넓히는 것이다.

## 잘하는 일
### 원인 모를 버그·재발 버그
- 수치로 규명한다(633×363↔643×373 → 스크롤바 되먹임). 스크린샷 단서로 Electron에서 재현해 원인 3개를 동시에 고쳤다. 요청 흐름 전체를 따라가 주원인+부수 버그 4개를 실제 API 호출로 확인했다
- 의장 가정(CSS)과 다른 원인(getBounds 반올림 되읽기)도 찾는다. 실기기 없는 듀얼 모니터 DPI 버그는 방어 수정+가짜 디스플레이 테스트를 하고 "원인 특정 못 함"을 정직하게 적었다
- 렌더 성능은 추측 대신 프로파일로 병목을 찾고 화면 픽셀 불변까지 증명한다. 나빠지는 맞바꿈도 스스로 보고한다

### 큰 merge·통합·이식
- 큰 merge에서 양쪽 의도를 살리고 상대 변경을 공용 훅으로 받는다. 멈춘 브랜치(커밋 안 된 작업 포함)를 인수한다. 이전 worktree·wip 커밋·멈춘 브랜치·커밋 id를 주면 이어받는다. 다른 위원 브랜치 병합·충돌 해결도 지시하면 해낸다
- 외부 앱 단계별 이식: 변경 전 커밋에서 옵션 조합 패치 해시를 뽑아 기존 동작 불변을 테스트로 고정한다. 검증 스크립트를 스스로 확장하고(MatchType 등 거짓 양성 처리), 다음 위원용 공용 구조(기능 등록표·잡 간 전달)를 만들어 쓰는 법을 RESULT에 적는다
- 변조 요청을 실제 서버로 보내 거절을 확인하고, 가짜 응답으로 그린 화면은 그렇다고 표시한다. 지시에 없던 보강(run_name 충돌 방지, 공개 폴더에 실존 인물 사진 미배치)을 이유와 함께 넣는다
- 31파일 대형 통합, 12파일 기능(외부 프로세스 필요 시 기동·유휴 종료·GPU 공유 락·잡 제출 훅·프론트 UI)을 effort high 단독으로 완주했다(테스트 34개 추가, 기존 테스트·lint·build 통과). 선행 위원의 벤치 코드를 정식 코드로 옮기고, 하위 호환(응답 필드는 요청이 보냈을 때만)·모든 제출 경로 훅·라이브 반영 위험(첫 로드 프록시 시간 제한, 고아 프로세스)을 스스로 보고한다
- 여러 모듈에 걸친 품질 개선·알고리즘 포팅을 한 번에, 전후 수치로 보고한다. 통합 반영 때 실험 결과와 바이트·프레임 일치를 확인한다(advisor 없이 175~200 calls 완주). Electron 창 떼기·붙이기 같은 큰 기능도 테스트를 붙여 한 번에 한다
- 될지 모르는 기능: "조사 → 큐가 비면 실측 → 되면 구현, 안 되면 RESULT만" 3단계로, 근거(파일:줄)와 수치 비교표를 내고 기본값도 근거로 정한다

### 구조 리팩터링 설계·동치성 검증 (high)
- 설계만 하는 작업(코드 변경 금지)을 주면 표 위주 계획서를 낸다: 읽는 곳·쓰는 곳 지도, 하드코딩 위치(파일:줄), 위험, 겹치지 않는 구현 분할까지 들어 있어 그대로 구현 지시로 쓸 수 있다. 서브에이전트로 탐색을 나눠 쓴다
- 구현 전에 같은 worktree에서 옛 체인으로 기준판을 다시 만들어 '기준 예외'를 먼저 찾고, 비교 명령과 결과를 RESULT에 남긴다([옛 커밋 기준판](common/git/git-restore-old-baseline))
- 후속 작업에서는 지시 밖이라도 실제 위험을 찾아 하위 호환 범위에서 고치고 보고한다
- 절차 전반은 [합본 생성물 충돌 없애기](common/git/split-combined-generated-files)
- advisor로 붙이면: 긴 설계 작업(sonnet 설계 위원 등)에서 계획을 확정하기 전에 상담하게 하면 안정적이었다

### 밸런스·수치 조정 (high)
- 시뮬레이션 반복으로 목표를 좁히고, 하네스 결함·교착 버그를 스스로 고친다. 기준선을 먼저 재고 전후 병렬 측정을 직접 만든다
- 밸런스 구멍을 적 종류별 피해 몫으로 분해하고, vi.mock 변형으로 요인 기여율을 나눈다. 고치기 전 코드를 git archive로 풀어 전후를 비교한다
- 엔진을 인자(시전자)로 일반화하고, "기존 동작 불변"을 시드 고정 54판 바이트 비교·화면 계산 스타일+픽셀 diff "차이 0"으로 증명한다. 경제 분석은 정적 계산을 게임 함수와 대조한 뒤 모의 플레이로 확인한다
- 불가능한 목표는 숫자로 보이고 a/b/c 선택지를 낸다. 넓은 수정이 다른 기준을 깨면 좁은 수정으로 물러나고, 지시 밖 대안은 RESULT에만 적는다. 숨은 오판정은 고치지 않고 보고한다. 다른 위원 몫 파일은 잘 피한다
- 지표가 "통과"여도 눈으로 결함을 찾아 검출기를 추가하고, 사람 눈 정답표로 정밀도·재현율을 낸다

### 원본과 맞춰야 하는 그림 재작업
- 로고: 다른 위원의 불합격 로고를 층 수치 측정으로 다시 만들고, 원인 추정을 8배 확대 비교로 검증해 '글자'가 아니라 '외곽선' 절단임을 바로잡았다. 지시 밖의 같은 문제도 찾아 고친다
- 투명화·자르기: 원인을 코드로 밝혀 예외 대신 일반 규칙으로 고친다. 수정 전 커밋에 새 검사를 돌려 결함 검출을 확인하고, 재실행 바이트 동일을 확인한다. 원본 탓과 스크립트 탓을 구분해 보고한다

### 영상 부분 재생성·접합·후처리 통합 (high)
- 짧은 잡 생성 → 접합 → 대사·효과음·BGM·쿵 재맞춤 → 구간 조각·Kdenlive까지 이어지는 긴 작업을 한 번에 끝낸다. 통합 위원으로 쓸 때 가장 믿을 만했다
- 생성 묶음 위원(영상 수정 30여 건): 충돌난 위원 브랜치 2~3개를 직접 병합하고, 패치가 CRLF 때문에 git apply에 실패하면 손으로 적용했다. 14구간을 순서대로 다시 생성하고 조립까지 4~5시간 걸리는 작업을 끝까지 했다. 점검 중 조립 스크립트 버그(말끝 잘림)를 스스로 찾아 고쳤고, 남은 한계(3회 시도 뒤에도 남은 흐름 등)를 솔직하게 적었다
- 같은 원인으로 두 번 막힌 작업(구멍 위치, 오빗)도 원인을 정확히 짚었다
- 다른 위원의 칠하기 결과가 미끄러진 원인(전체 호모그래피+평활)을 짚고 조각별 KLT affine으로 다시 합성해 0.04px/f로 낮췄다. 같은 작업에서 "빠진 동작은 이전 사용자 결정으로 뺀 것"을 커밋·문서로 증명했다
- 사용자 스크린샷을 실제 프레임과 대조해 시각→구간·키프레임을 정확히 맞춘다(사용자 시각이 2~9초 어긋나도). 사용자가 지칭한 구간 id가 틀렸을 때(조각 번호와 혼동) 캡처 프레임으로 실제 대상을 찾아낸다
- 증상 뒤의 원인(구도·옛 수정안 append 문장·구간 안 자체 컷, 끝 가이드 스냅 등)을 직접 찾아 시도 2에서 고친다. "시도 최대 2회" 같은 한도를 지킨다
- 계획과 다른 점(컷 길이, 도착 시각, 입 어긋남)을 숫자로 먼저 보고한다. 지시와 다르면 이유를 적고 보수적으로 간다

### 프리비즈→영상 같은 긴 창작 파이프라인 (high)
- 프리비즈를 12컷 motion-timeline으로 분석하고, 위키의 정리 방법(HSV 마스크)이 안 맞자 rembg 두 모델을 합성해 정리본을 만들었다. Codex 키프레임 12장을 3갈래 병렬로 그리고, 구간 생성(front:true 순서 — 앞 잡이 실행에 들어간 뒤 다음 잡 제출)·조립본·비교본·스크린샷·README까지 재배정 없이 끝냈다(158 calls, 약 55분)
- 액션 드래프트 반복 수정에서도 키프레임, 다구간 영상 생성, 후처리, 조립까지 이어지는 긴 파이프라인을 안정적으로 끝냈다
- 원인 분석에 강하다: 화살 경계 문제를 프레임 추적으로 규명했고, 화살이 화면에서 위로 떠 보이는 이유를 소실점 원리로 설명했다. 같은 문제로 sonnet이 두 번 막힌 뒤(화면 기울기만 잼) 재배정하자 화면 이동 각도 기준으로 해결했다
- 지시의 가정을 그대로 믿지 않고 검증한다: 검이 사라지는 문제를 지시대로 전용 검 시트로 대응한 뒤, 같은 시드 비교로 결함이 그대로인 것을 확인하고 원인을 프리비즈의 휘두름 부채꼴로 바로잡았다(근거 캡처 남김)
- 생성을 기다리는 동안 스크린샷·README를 미리 만들어 의장이 중간 결과를 바로 보여 줄 수 있게 한다
- 판단을 맡기면("카메라 이동을 지울지 판단하고 이유를 적어라") 사용자 의도를 기준으로 정하고 근거를 README에 적는다
- 추적 파일(work/image-run.log)이 바뀌면 스스로 되돌린다

### 기록에서 규칙 추출·스킬 문서 개정·권고 점검기 (high)
- 검토 문서 수십 개·git 이력·위키에서 재사용 규칙을 뽑아 스킬 문서와 점검 스크립트에 한 번에 넣었다(111 calls, 약 15분). 규칙마다 "규칙/왜/적용"과 출처 경로·실측값을 달고, 옛 규칙과 충돌하는 곳은 날짜와 근거로 교체한다
- 권고 검사 6개+테스트를 넣고 기존 테스트 통과를 유지했다. 고친 데이터와 안 고친 데이터에 점검기를 돌려 대비로 규칙이 맞는지 보였다
- 보수적 판단이 적절하다: validate 게이트·스크립트 기본값은 기존 데이터를 깨뜨리므로 건드리지 않고 문서 권장으로만 두었다. 원래부터 실패하는 validate를 "이번 변경과 무관"으로 분리 보고한다

### 진단·정리·계획서·문서
- 저장소 진단: 읽기 전용을 지키며 어디가 몇 GB인지, 단계별 절감량, 판정 표를 숫자로 낸다. 쓰레기 속 재생성 불가 원본 같은 위험을 스스로 찾는다
- 되돌릴 수 없는 정리(백업 저장소 이관+삭제)는 검증→삭제 순서를 지키고 지시보다 넓게 백업한다. 메인 폴더 정리도 바이트 대조 후 삭제하고, 머지를 시험하고, 게임 변경 여부를 정확히 보고한다. 잃은 원본도 숨기지 않는다
- 세션과 뗀 1000h 측정을 완주한다. 계획서는 파일 경로·분할까지 바로 쓸 수준이다
- 역기획서: 탐색 에이전트를 주제별로 병렬로 돌리고, 엇갈린 값은 코드를 직접 열어 확인한다. 문서·메모와 코드가 어긋난 곳과 정리 후보까지 뽑는다
- 합성 효과음 설계에서 측정으로 지시의 방식이 나쁘다는 걸 증명하고 대안을 골랐다(청취 확인은 못 하니 사용자 청취 단계가 필요)

## 약한 일
- 제약이 없으면 숨은 배율(전용 계수)을 새로 만든다. 설계 의도를 모르면 가장 쉬운 레버를 고른다
- '바꾸지 말 것'이 있으면 목표가 깨져도 보고만 한다. 결정 규칙을 지시 글자 그대로 적용해 실험보다 엄격해진다. 지시 범위를 문자 그대로 지킨다("버튼 문구만" → 패널 제목은 그대로)
- 완료 조건을 문자 그대로 지키다 목적을 놓친다: "머리 ≡ 기준"을 맞추느라 단위별 파일 머리에 전 단위 목록을 넣어, 다른 단위 추가 때 충돌할 원인을 남겼다(RESULT의 '가정'에는 적었다)
- 반대로 "기존 동작 유지"를 자기식으로 해석할 때가 있다(기존 테스트 단언을 좁힘) → 결과 보고에서 직접 확인한다
- 금지 조항과 사용자 요청이 부딪히면 금지를 따라 요청 일부를 빠뜨린다(예: 통합 지시의 "새 생성 금지" 때문에 사용자가 요청한 톤 보정이 음량 보정만 됐다)
- 소리는 들을 수 없어 귀로 확인할 곳을 남긴다
- 측정 산출물(원자료 수백 파일, JSON 수만 줄)을 커밋에 넣는다
- 작업이 길다(100~200 calls, 한 작업 1~1.5시간, 대량 재생성 묶음은 4~5시간). 앱 재시작에 약하다. 긴 작업 도중 멈추면 RESULT.md가 없어 의장이 산출물을 읽어 정리해야 한다
- 병렬 위원과 같은 파일(공용 생성 파일 포함)을 건드리면 끝난 뒤 충돌 해결이 따로 필요하다
- 스크린샷 일부만 직접 열어 보고 나머지는 "열어 보지 않았다"고 적는다. 시안 합격 보고 때 경계 잘림을 놓친다. QC 표시가 남은 칸을 '안 보임'으로 넘길 때가 있다
- 범위를 스스로 넓힌다(영상 구간 재생성 등)
- 다시 내려고 공용 ComfyUI 대기열에서 자기 대기 잡을 /queue delete로 지운다(자기 잡만 지우고 기록도 남겼지만, 지시가 없으면 위험하다)

## 지시에 넣을 문구
- 사용자 원문 인용 + "하지 말 것"(예: "A 쪽만 조정, 배율 X 금지") + "추측으로 고치지 말고 원인을 숫자로"
- 금지와 사용자 요청이 부딪히면 예외를 지시에 명시한다(예: "새 생성 금지, 단 N번 톤 보정은 새 생성 허용")
- 완료 조건: summary 표, 목표별 달성 여부, "못 맞춘 칸은 숨김없이", 전후 캡처 목록. 비교 기준(같은 시드 전후 수치), 눈 확인 필수, 쓰기 허용 폴더
- 완료 조건에는 목적도 함께 적는다(예: "머리 ≡ 기준" 옆에 "다른 단위가 바뀌어도 이 파일은 불변")
- 구조 리팩터링: 범위 파일 목록 + 하지 말 것 + 측정 가능한 완료 조건(바이트 비교, 한 단위만 다시 만든 뒤 다른 단위 git diff 없음, 가짜 새 단위로 불변 확인)
- 커밋 범위: "원자료 커밋 금지 범위", "요약 표만 커밋", "가장 급한 것 먼저 커밋"
- 확정 기준의 기억 id. 비용 영향 규칙엔 "실험 판정과 같게 유지" 같은 기준
- "남긴 png는 모두 직접 연다", "중간 결과도 RESULT.md에 수시로 적는다", 경계 확대 비교를 완료 조건에
- 그림 재작업: 의장이 본 문제를 번호로 적고 비교 시트를 직접 열게 한다. "어두운 배경·체크무늬 확인 시트를 모두 직접 열기", "바뀐 칸과 이유 보고". 의장이 시트를 다시 본다
- 영상 통합: 선례 스크립트 경로와 공유 기억 id 나열, 완료 조건 수치(LUFS·받아쓰기·md5), "구간 id보다 타임코드·캡처를 믿어라", 결과물 경로·비교 클립 크기 고정, 시도 횟수 상한
- 생성 묶음 위원: 병합할 브랜치 목록과 충돌 파일, 반영할 계획서 경로, 다시 생성할 구간, "GPU 대기열에서 다른 사람 작업 취소 금지"([설계 위원 병렬 + 생성 묶음 위원](common/council/council-live-testing-batch))
- 창작 파이프라인(프리비즈→영상 등): 위키 경로 목록과 사용자 선호 방식, 완료 조건에 비교 영상·shots·README의 '남은 약점'·'다음 판 제안'. 공용 대기열이면 "자기 prompt_id만 지운다"를 명시한다
- 규칙 추출·스킬 문서 개정: "읽을 근거 목록 + 넣을 파일 범위 + 게이트는 강제하지 말고 권고로 + 기존 데이터에 돌린 결과 수치를 보고". 기존 테스트를 고쳤으면 무엇을 바꿨는지 따로 보고하게 한다
- 이식·통합: 이전 단계 RESULT.md 경로·선행 벤치 코드를 "먼저 읽을 것"으로 주고 "다음 기능을 위한 구조를 설명하라"를 붙인다. 같은 파일을 만지는 병렬 위원을 미리 알리면 충돌 지점을 RESULT에 적는다. 생성 산출물 충돌은 재빌드로 풀린다고 미리 적는다
- 바꿀 UI 문구 범위(제목·설명문 포함 여부)를 명시한다. 실측엔 "큐가 빌 때만, N회" 상한
- 버그 규명·통합: 시작 파일 목록, 의심 지점 예시, "양쪽 기능 유지"
- 정리: "제외 목록, 하지 말 것(gc·push)". 진단만 시키는 단계를 먼저 두면 사용자 결정 질문이 선명해진다
- 범위: "다른 구간 재생성 금지, 이유 있으면 보고"
- 배정: 원인 미상·재발 버그, 다른 위원이 실패한 작업의 원인 재진단·재시도, 브랜치 통합+긴 실행이 섞인 일, 영상 재생성→접합→후처리 통합, 여러 위원 브랜치 병합+대량 재생성 묶음, 분석→그림→생성→조립 창작 파이프라인, 구조 리팩터링 설계·동치성 검증, sonnet이 두 번 막힌 기하·원인 분석 문제는 처음부터 opus 한 명에게. 호출 수가 많아 주간 사용량이 빠듯하면 범위를 좁힌다. 정확성이 중요한 장은 opus에게. 결과(표+한 줄 결론+가정 바꿔 보기)는 의장이 바로 사용자 결정 질문으로 잇는다
